## Recommendation

Use the vinext Build Worker, one Build-owned D1 database, and private R2 storage. Run a bounded model/tool loop inside the HTTP response that the open generation tab consumes. D1 owns project access, conversation records, generation attempts, immutable-version metadata, revision checks, and spending reservations. R2 owns file bytes, complete manifests, and any accepted image uploads. Keep the last complete version readable throughout an attempt. Publish to Drop only through a separate, explicit user action.

Replace fx0's current durable-agent orchestration with this small loop. Retaining libfx's explicit WASM engine is technically plausible, and the offline check below succeeded. It is not a drop-in port, however. Both choices still need new multi-file tools, D1/R2 persistence, funding enforcement, cancellation fences, and the Build-to-Drop publication boundary. The explicit loop makes every paid transport attempt visible to the budget owner and avoids maintaining opaque engine journals for a release that deliberately stops on interruption.

Recommend `gpt-5.4-mini-2026-03-17` through the OpenAI Responses API as the single candidate for later approval, initially provider-direct. It has documented coding, streaming, function-calling, and structured-output support. Compare it with the lower-priced Claude Haiku 5.5 only in a later approved quality experiment. This report selects neither an allowance nor a platform spending cap. Current prices and reproducible estimates appear below.

Everything described as a design or recommendation below is proposed, not implemented. Verified facts have sources or recorded checks. No vinext runtime integration, deployed Worker, real model quality, provider account access, or D1/R2 failure behavior was tested.

## libfx 0.0.14: retain or replace

The exact published package, rather than a claim of general Node compatibility, establishes these requirements:

1. The root export resolves to `node.js` under the Node condition. That loader imports Node filesystem/module APIs and loads platform-specific `.node` addons. Its fallback needs JSPI. `nodejs_compat` alone does not establish that a native addon will load in Workers. See the versioned [package exports](https://unpkg.com/libfx@0.0.14/package.json), [Node loader](https://unpkg.com/libfx@0.0.14/node.js), and Cloudflare's [partial Node API support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/).
2. The package documents native macOS/Linux x64/arm64 support, and JSPI-based WASM elsewhere and in browsers. Default durable storage is Vercel Workflow World/Queues on Vercel, local files on Node, and memory in browsers. Those defaults do not provide Build's D1/R2 persistence. See the published [runtime and durability documentation](https://unpkg.com/libfx@0.0.14/README.md).
3. `libfx/browser` constructs asset URLs with `new URL(..., import.meta.url)`. Our bundled workerd probe failed at startup with `TypeError: Invalid URL string`. `libfx/wasm`, which exports `fx-sdk.js`, accepts an explicit precompiled `WebAssembly.Module`. That path avoids the asset-URL problem and worked locally. Workers documents precompiled WASM modules, not arbitrary runtime compilation as a portable loading strategy. See [browser.js](https://unpkg.com/libfx@0.0.14/browser.js), [wasm-module.js](https://unpkg.com/libfx@0.0.14/wasm-module.js), and [Workers WASM](https://developers.cloudflare.com/workers/runtime-apis/webassembly/).
4. `fx-sdk.js` tests for `WebAssembly.Suspending` and `WebAssembly.promising`; it uses them for asynchronous host operations. A custom provider uses OpenAI Chat Completions at `{baseUrl}/chat/completions`, with optional per-model context/output/tool/vision metadata. Keys are attached at the JS transport boundary. This can remove the Vercel provider dependency, but it is not a general native Responses or Anthropic Messages adapter. See [engine source](https://unpkg.com/libfx@0.0.14/fx-sdk.js), [custom-provider.js](https://unpkg.com/libfx@0.0.14/custom-provider.js), and [exact declarations](https://unpkg.com/libfx@0.0.14/types/libfx.d.cts).

The offline test used `workerd@1.20261023.1`, compatibility date `2026-10-23`, and esbuild `0.25.12`. It imported the explicit WASM SDK and embedded `fx-core.wasm` as a module. Engine construction succeeded with zero fetches. A second test supplied two synthetic OpenAI SSE responses through an injected `fetch`, first requesting a host `stage_file` tool, then returning text. Results were `supportsJspi: true`, one tool execution, two intercepted requests to `https://invalid.example/v1/chat/completions`, and `stopReason: end_turn`. Both requests carried `max_tokens: 4096` from the custom-provider metadata. All transport responses came from the fixture; it performed no real model calls or external inference requests.

That proves a small WASM execution path, not production compatibility. It did not measure hosted CPU/memory or startup, actual-provider protocol differences, persistence restore, cancellation races, vinext bundling, or concurrent engines within the shared 128 MB isolate.

If retaining libfx, use a request-owned `createFxEngine` from the explicit WASM entry, not the existing global `createFxAgent` defaults. Save only completed conversation/checkpoint state needed for the next user turn, or implement its fenced persistence interface if opaque journals are justified. Do not automatically resume unfinished turns. The host must still guard every send and tool. In particular, `fx-sdk.js` retries thrown transport failures up to twice; the budget gate must reserve a fresh physical-attempt identity on each invocation of the injected fetch. Existing conversation-hash deduplication must not make a second send free in the ledger. The explicit loop avoids this hidden retry layer and permits the native provider API.

## Request execution and the platform envelope

Workers HTTP execution has no hard wall-clock duration limit while the client remains connected. Disconnects or completed responses can cancel associated work; `waitUntil()` adds at most 30 seconds. Network waiting does not consume CPU time. Current limits are 128 MB per isolate, six outgoing connections awaiting headers, 10 ms CPU on Free, and 30 seconds default CPU on Paid with a configurable maximum of 300 seconds. Paid permits 10,000 subrequests by default; Free permits 50. Worker bundles are currently limited to 64 MiB uncompressed, with one-second startup. Free/Pro request bodies are limited to 100 MB by the account plan. These are platform ceilings, not sensible application limits. [Workers limits, updated October 12](https://developers.cloudflare.com/workers/platform/limits/).

Recommend Workers Paid for the actual vinext application and generation path. A streamed response with heartbeat events fits tab-open generation. Keep the loop attached to the response's lifetime; do not return an acknowledgement and expect an unobserved promise to survive. Use an application wall deadline, per-call total and idle deadlines, upstream abort signals, response-byte limits, and a hard number of inference sends and tool operations. Stop and retain the last complete version when any bound is reached. `maxDuration = 800` from the Vercel route is not a Workers execution policy.

Use one sequential model call and sequential file writes initially. Bound prompt/history bytes, input tokens including tool schemas/results, output tokens including reasoning, total output across calls, tool argument/result bytes, file count, per-file bytes, total version bytes, and upload storage. Validate all bounds server-side. Stream events to the tab, but persist messages, attempt transitions, and complete tool results at bounded boundaries rather than writing one D1 row per token. A question that needs user input should end the attempt and await a new user turn rather than keep a paid generation open indefinitely.

D1 Paid limits include 10 GB per database, 1 TB total account storage, 1,000 queries per Worker invocation, 2,000,000 bytes per row/string/BLOB, 100 bound parameters, 100 KB SQL text, and 30 seconds per query. Free has 500 MB per database and 50 queries per invocation. Each database executes queries one at a time. Keep metadata small, index ownership/project/version/attempt lookups, and put file and long transcript bytes in R2. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

R2 allows 1,024-byte object keys, 8,192-byte object metadata, 5 TiB objects, and 5 GiB single-part uploads. Rewriting the same key more than once per second can fail. Use unique immutable object keys, and much smaller product limits. R2 is strongly consistent through its storage APIs; a CDN cache can retain old responses. Keep drafts private and use immutable version URLs. [R2 limits](https://developers.cloudflare.com/r2/platform/limits/), [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).

## Minimal ownership and code boundaries

Proposed logical records, all scoped by the authenticated account subject:

- `projects`: owner ID, revision, latest complete version ID, optional active attempt and fencing epoch, and a Build-origin Drop site association. Account identity comes from the shared identity contract; Build does not gain unrestricted Drop database access or cross-app cookies.
- `messages` and `attempts`: bounded conversation content/references; parent version/revision; idempotency key plus request digest; model, policy and price versions; running/completed/cancelled/failed/interrupted status; deadline/lease; failure reason; resulting version ID.
- `versions`: immutable ID, parent ID, complete manifest key/hash, total bytes, creation time, and creating attempt. A complete manifest enumerates every path, object key/hash, MIME type, and byte length. A version must not depend on replaying an edit chain.
- `attempt_files` and `assets`: temporary overlay/tombstones, tool-call receipts, object ownership, validation state, byte reservations, and eventual cleanup state. Reuse unchanged immutable objects rather than copy them for every version.
- `budget_buckets`, `reservations`, `inference_calls`, and settlement receipts: account and global liabilities, period IDs, request/send identity, token bounds, price snapshot, provider request ID, actual usage, and unknown-charge state.
- `publication_requests`: user-selected immutable version, request identity, remote receipt, and publication status. Drop remains the authority on what is live, billing, and domains. Build-origin provenance must be verified by trusted application metadata. A foreign Drop site ID is insufficient.

Keep framework routes thin. Proposed modules are `generation/runner`, `generation/provider`, `generation/tools`, `projects/store`, `versions/store`, `assets/store`, `funding/ledger`, and `publication/client`. These are boundaries for later implementation, not files added by this research. The runner owns deadlines and attempt transitions; the provider owns request serialization, streaming parsing and usage; the ledger authorizes every send; storage enforces ownership and conditional changes; publication never belongs to the model's tool set.

Start with `list_files`, bounded `read_file`, `write_file`, `delete_file`, and optionally exact-match `edit_file` with an expected file hash. Reads see the pinned base plus the attempt overlay. Writes stage complete file contents and return receipts; they cannot change the project head or publish. The host finalizes a version after successful generation and validation. Tools receive an already-authorized project/attempt context, never a model-chosen account or bucket prefix. Reject traversal, absolute paths, duplicate normalized paths and invalid MIME/path combinations. No shell, packages, arbitrary build execution, remote MCP, subagents, or provider-hosted search are required.

## Complete versions and concurrency

1. Authenticate and authorize the project. Deduplicate the submitted command by account-scoped idempotency key and request digest. Pin `baseVersionId` and expected project revision. Atomically claim a generation slot/fencing epoch. Prefer one active attempt per project; concurrent requests receive the existing attempt or a conflict.
2. Stage only changed files under unique immutable keys. Keep the base manifest unchanged. Validate each fully received tool call before executing it; streaming JSON fragments are display-only. Persist each accepted tool receipt so a repeated call ID with the same content returns its prior result. Reject the same ID with a different digest.
3. Merge the base manifest, writes, and deletions into a complete new manifest. Verify all referenced bytes exist, hashes/lengths match, internal HTML links and CSS/JS references resolve, and the result satisfies the static-site contract. HTML, shared external CSS/JS, and permitted asset files are the output; no generated server runtime is needed.
4. Write the immutable manifest to R2 and await success. Then use one D1 transaction to record completion and conditionally advance the project revision/head, requiring the pinned revision, current fencing epoch, owned project, and running attempt. D1 `batch()` is transactional and rolls back on statement errors. A conditional UPDATE affecting zero rows is a conflict, not an SQL exception: make dependent statements conditional too, or enforce a failing constraint/trigger so an apparent success cannot partially commit. Inspect the authoritative receipt after an ambiguous response. [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/).
5. Resolve a lost final acknowledgement by reading the attempt's completion receipt, not by generating again. Older attempts must never replace a newer head. A fully validated conflicting version may be retained as detached history if product policy permits; otherwise retain it only for cleanup. Do not mark it the current draft.

There is no atomic transaction across D1 and R2. This ordering makes a crash before the D1 commit leave unreferenced objects rather than a visible half-written version. A later authenticated request or bounded maintenance sweep can clean orphaned staging data. Do not apply an unconditional TTL to blobs that a completed version references. Garbage collection must account for completed manifests, uploads, active attempts, retained versions, and publication exports, with a grace period for in-flight writes.

Use the D1 primary for admission and finalization. Read replication is opt-in through Sessions, and ordinary queries otherwise use the primary. Do not authorize spending or writes from a stale UI read. [D1 read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/).

Generation updates only the saved working draft. Explicit Publish names one completed version and creates a separate idempotent transfer request to Drop. A later draft cannot change the bytes of that request. Export the entire manifest and asset set, and update Build's publication receipt only after Drop confirms success. The integration protocol and Drop-side concurrency policy belong to the publication ticket; this research did not inspect or modify Drop.

## Failure, cancellation, and retry

Recommend a durable state machine whose terminal status cannot be reopened by late callbacks. Cancel first records a fence in D1. The running request aborts upstream work when it observes that fence, on stream cancellation/disconnect, or at its deadline. Check the fence before every paid send, before accepting tool effects, and during finalization. This may not interrupt an upstream call immediately, but it prevents late bytes from becoming the draft head.

If the Worker dies without cleanup, a stale lease/deadline lets a later request mark the attempt interrupted and offer Retry. The stale attempt remains fenced. No background generation resumes. Retry creates a new attempt from the last completed version and preserves the failed prompt/status in chat. If finalization had already committed, return that version instead. Completion and cancellation race through the same D1 conditions: whichever commits first determines the result.

A model timeout, connection loss, or user cancellation does not prove zero provider cost. The provider may already have processed input or generated output. Retry cannot promise the same result, a free second attempt, or exactly-once inference billing. Application idempotency prevents duplicate admission and version creation; it does not establish provider inference idempotency. Do not automatically replay an ambiguous call.

## Enforceable spending admission

Use integer monetary units with upward rounding and a versioned rate schedule. A generation-count allowance, if chosen later, is an additional atomic entitlement; it cannot replace monetary limits. Apply both account and global limits to the same admission operation, including all in-flight reservations and unresolved liabilities. Rate limiting and verified signup can reduce abuse, but many accounts can still spend the shared fund, so the global gate is essential.

For each physical inference send, compute a conservative bound `R = ceil(Imax * input_rate + Omax * output_rate + any enabled fixed fees)`. Include system instructions, conversation replay, tool definitions/results, image tokens, and billable reasoning. Do not assume a cache hit. Reserve `R` before transmission, in the same D1 database for both account and platform buckets. If using a turn-wide reservation instead, reserve the sum of every permitted send and explicitly allocate it per call. No model call starts if the ledger is unavailable or its admission result is ambiguous.

Avoid separate read/check/write HTTP calls. A practical SQL design is a uniquely keyed reservation INSERT whose transactional triggers check and update both bucket counters, rejecting any invariant violation. A carefully guarded `batch()` with a constraint-based rollback is another option. The invariant is `settled + reserved + unknown <= limit` for every applicable bucket, and all affected rows must move together. Check constraints must forbid negative or overflowing counters. A zero-row conditional UPDATE must not let the other bucket debit succeed. This design requires a real D1 concurrency proof before launch; it was not implemented here.

Pin each reservation to its original account/global period IDs. Resetting an allowance must not release outstanding charges or start a new period with uncounted liabilities. Also retain an overall platform liability cap if periodic limits are selected. Limit active generations and use atomic storage-byte reservations to stop free signup from exhausting R2 independently of inference.

Claim `reserved -> dispatching` with a conditional state update before sending. Only the caller that wins that transition may send; a duplicate handler must read the existing receipt/status. Then record the provider request ID and final usage when available. Exactly-once dispatch across a database commit and an external API is not available here. A crash between dispatch-state recording and network send is indistinguishable from a charged call whose response was lost. Treat it conservatively.

- With trusted final usage, atomically replace that call's reservation with the actual charge and release only the difference. Deduplicate settlement by call identity.
- With a proven pre-dispatch failure, release the reservation once.
- With a partial stream, cancellation, timeout, lost usage or uncertain dispatch, move the full bound to an unknown-charge hold. Never refund merely because a lease expires. The attempt can become retryable while its financial liability remains held.
- Reconcile later from trustworthy provider/Gateway usage and request identifiers. If request-level evidence is unavailable, retain the worst-case charge or require operator settlement; a guessed zero must not restore the platform budget. A separate client-facing courtesy refund, if policy later permits one, must not erase Simplenet's liability.

Retries consume a new physical-send reservation even for identical bodies. Disable SDK/Gateway automatic retries and fallbacks initially. Where a retry layer cannot be disabled, its maximum sends must be included and individually accounted for. Stop all sends if actual charges exceed a reservation or the price configuration becomes stale. Local enforcement bounds approved inference liability under the chosen API's documented token limits and pricing; it does not bound taxes, unrelated credentials, provider billing mistakes, or all Cloudflare infrastructure charges. Use provider-side controls and a platform kill switch as secondary protection, not a substitute for reservations.

An exact token count or a justified upper bound is required for input admission. A character/byte estimate is not automatically valid across tokenizers. Until the tokenizer/counting path is proved, reserve against the model's full permitted input envelope or reject an unbounded request. Never feed an unlimited saved transcript into the next call. If image analysis is retained, include its provider-specific token rules before enabling it for funded generation.

## Provider-direct versus Cloudflare AI Gateway

Recommend direct provider HTTPS first, through a tiny transport adapter using Worker secrets. It has fewer credentials and intermediary behaviors to validate, and makes the paid-send boundary clear. The adapter should also permit a later Gateway base URL without changing tools or storage. Secrets never enter model-visible prompts, saved projects, browser code, or generated files.

AI Gateway can proxy native OpenAI Responses/Chat Completions and Anthropic Messages, add logs and operational controls, and use supplied/stored provider keys. That does not mean Cloudflare executes those models. Workers AI and Gateway Unified Billing are separate execution/billing paths. Native endpoints are documented in [Gateway OpenAI](https://developers.cloudflare.com/ai-gateway/usage/providers/openai/) and [Gateway Anthropic](https://developers.cloudflare.com/ai-gateway/usage/providers/anthropic/). Do not use fx0's Vercel Gateway transport for either path.

Gateway's optional Unified Billing purchases credits, charges a 5% fee on those purchases, and can produce a negative credit balance that is billed later. It is not a strict prepaid platform cap. Keep the direct-price estimates above separate from this additional fee and verify the exact model/path is supported before choosing it. [Unified Billing](https://developers.cloudflare.com/ai-gateway/features/unified-billing/).

Gateway's current spend limits are explicitly eventually consistent: request cost is recorded after completion, allowing concurrent bursts to exceed a limit. Its request-count rate limits also do not reserve dollars. They can supplement, but cannot replace, the D1 account/global ledger. [Gateway spend limits](https://developers.cloudflare.com/ai-gateway/features/spend-limits/), [rate limiting](https://developers.cloudflare.com/ai-gateway/features/rate-limiting/).

Gateway supports automatic retries; its request timeout concerns time to the first response portion, not the complete stream. Disable retries, fallback routing and generation caching initially, and keep the application's total/idle stream deadline. Verify effective gateway-level settings as well as request headers. Avoid raw prompt/source logging by default; request IDs, bounded usage metadata and redacted diagnostics are sufficient for the first operational proof. [Request handling](https://developers.cloudflare.com/ai-gateway/configuration/request-handling/), [Gateway logging](https://developers.cloudflare.com/ai-gateway/observability/logging/).

## Why no Durable Objects or Agents SDK initially

D1 transactions already provide durable conflict checks and shared budget admission. A request-owned loop supplies the tab-open execution lifetime. Complete manifests and the transcript let a new request reconstruct the last completed state. A durable per-project process is not required to satisfy those conditions.

Durable Objects provide uniquely addressable compute and strongly consistent attached storage. They would help if measured D1 admission contention or cross-request cancellation latency becomes unacceptable, or if collaborative live editing becomes a requirement. Adding one object per project would not by itself serialize a shared platform budget: that still needs one global authority or conservatively preallocated budget blocks. It also would not make a provider call and storage commit atomic. [Durable Objects properties](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/).

Cloudflare's Agents SDK adds session identity, local SQL, connections, scheduling and recoverable execution. Those are useful when continuing independently of the tab or supporting multiple live channels is wanted. Current requirements explicitly accept interruption plus Retry. Adopting the SDK would add another state owner and recovery policy to prove. Reconsider it only after a changed requirement or a measured acceptance-test failure establishes a need. [Current Agents runtime](https://developers.cloudflare.com/agents/).

## Images, retention, and unchosen policy

Store accepted uploads privately in R2 with D1 ownership, type/length/hash metadata and byte reservations. Validate MIME using file bytes and enforce decoded size/dimension limits. Refer to uploaded assets by server-issued handles; include an image in model context only when analysis is approved and its cost is bounded. A placed asset may be copied into the publication without sending it to the model. Keep base64 out of ordinary D1 rows and saved chat JSON.

This storage design accommodates images but does not choose upload count/size, remote-image fetching, generated images, resizing, or supported formats. Remote fetch would need a separate bounded SSRF-safe path; image generation would need its own price reservation. Both can remain disabled. Source HTML/CSS/JS, manifests and uploaded bytes all count toward account storage and retained-version limits, whose amounts remain open. History retention, deletion/export rules, orphan-cleanup cadence, and Drop export retention require decisions before launch.

Other open decisions are allowance unit/amount, reset rules, account and platform caps, behavior on exhaustion, client treatment of failed/unknown charges, maximum pages/files/bytes, and the shared identity/publication contract. None is settled by the arithmetic or experimental execution bounds in this report.
